# Logo crop cache is keyed by mtime and can serve a stale crop for a same-size asset with an older timestamp

**ID:** BUG-485
**Date:** 2026-10-20
**Resolved:** resolved
**Commit:** 5408a33da1772b1e8b96235850db8cfd4143d103
**Issue:** #485

## Original Issue Body

The AI Venture Studio deck generator caches its pre-cropped logo in the temp dir and re-cuts it only when the source asset is **newer** than the cache:

```python
# scripts/presentation/generate-ai-venture-studio-deck.py
source_mtime = os.stat(LOGO_PATH).st_mtime_ns
if not os.path.exists(out) or source_mtime > os.stat(out).st_mtime_ns:
    ... re-crop ...
```

mtime is not content identity. If `brand/logo/logo-full.png` is replaced by a file whose mtime is **older** than the cached crop (backup restore that preserves timestamps, an artifact copy, a build step that sets timestamps), the stale crop is silently reused and the deck ships with the wrong logo.

Why the cache key was not already a content hash: the cached filename becomes the picture's `descr` inside the .pptx, so the deck XML must not vary between machines. A hash- or mtime-suffixed cache name would make the artifact differ per machine and break the drift guard `test_committed_deck_matches_the_generator` (which compares the committed deck against a fresh build).

## Root Cause (filled by the resolving engineer)

The cache used file modification time as a proxy for content identity. Any write path that produces a new file with a timestamp at or before the cache's timestamp (a restore that preserves timestamps, a copy, a build step that normalises mtimes) makes the freshness check report "up to date" and the stale crop is reused. The deck generator had no content-based check, so nothing detected the substitution.

The constraint that forced the mtime approach in the first place was real: python-pptx derives the picture's `descr` from the file name it is given, so the cache file name leaks into the deck XML. Keying the cache by content alone would have made the artifact differ between machines and broken the drift guard.

## Fix (filled by the resolving engineer)

Decoupled the cache key from the artifact identity:

1. `_cropped_logo()` computes a SHA-256 digest of the source asset and caches the crop under `ai-venture-studio-lockup-880x713-<sha8>.png`. Different content can never share a cache entry, whatever the timestamps say. It returns `(cache path, stable name)`.
2. `logo()` sets the picture's `descr` explicitly to the stable name `ai-venture-studio-lockup-880x713.png` after `add_picture`, so the content-addressed cache file name never reaches the deck XML and the artifact stays byte-identical across machines.
