## Original Issue Body

`tests/performance/test_dashboard_performance.py::TestAPIPerformance::test_endpoint_response_time_p95[/api/v1/org-chart]` fails intermittently in CI with a ~2 ms overshoot.

Observed on PR #483 (2026-10-20, `Test (ubuntu-latest)`):

```
AssertionError: /api/v1/org-chart P95 response time 202ms exceeds 200ms.
All times: ['4.8', '4.4', '201.9', '4.4', '4.0', '3.9', '3.7', '3.9', '3.7', '3.8']
```

Nine of the ten samples were ~4 ms; one outlier at 201.9 ms failed the gate. The same test passed on `windows-latest` in the same run and passed on re-run. PR #483 changed no `src/` code, so the failure is a pre-existing flake, not a regression from that work.

Root cause (three compounding defects in the test):

1. **The metric is not a P95.** `p95 = sorted(times)[int(len(times) * 0.95)]` with 10 samples resolves to index 9, i.e. **the maximum**. A single outlier fails the gate.
2. **No warm-up.** Early requests pay lazy imports and cold file I/O.
3. **The threshold is miscalibrated.** 200 ms is ~50x the typical 4 ms, so the gate can only trip on runner jitter, and would *not* catch a real 10x regression (40 ms).

Contributing inefficiency: `get_org_chart` calls `_load_registry()` on **every request** (`src/ai_company/dashboard/api.py`), which re-reads and re-parses `company/agent-registry.json` from disk and re-normalizes every agent dict. That is the ~4 ms baseline and the cold-I/O spike. Ten-plus endpoints share this path.

## Root Cause (filled by the resolving engineer)

The test's statistic and threshold were both wrong for the environment, and the endpoint it measured had an avoidable per-request cost.

- The "P95" was the maximum of ten samples, so the gate had the variance of a maximum with the sample size of a percentile. A single slow read on a contended runner - not a regression - decided the result.
- The 200 ms limit was calibrated nowhere: it sat ~50x above the typical response, so it could not distinguish "slow machine" from "broken endpoint".
- Underneath, every registry-backed endpoint re-read and re-parsed a 96 KB JSON file per request, so the baseline the gate measured was dominated by I/O rather than by the endpoint's own work.

## Fix (filled by the resolving engineer)

1. **Recalibrated the gate** (`tests/performance/test_dashboard_performance.py`): drop a warm-up request, take 20 samples, assert a **median** against a **per-endpoint budget** calibrated from measured latencies at 3-5x headroom, and keep a load-tolerant 2000 ms ceiling. Per-endpoint budgets were needed because the endpoints differ by an order of magnitude (`/api/v1/agents` 11 ms median against `/api/v1/models` 90 ms).
2. **Cached the registry read** (`src/ai_company/dashboard/api.py`): `_load_registry()` parses the file once per revision, keyed on the file's **path, mtime and size**, so a write - including one made by another process, such as the registry writer behind `PATCH /agents/{name}/reports-to` - invalidates it immediately rather than after a TTL. Callers get per-call normalized copies, so no mutable state is shared.
3. **Pinned the contract** (`tests/unit/test_dashboard_registry_cache.py`): read-once while unchanged, immediate invalidation on rewrite, legacy camelCase normalization still applied, and no shared state between callers.

## Files Changed

- `tests/performance/test_dashboard_performance.py` - warm-up, 20 samples, median against a per-endpoint budget table, load-tolerant ceiling.
- `tests/unit/test_dashboard_registry_cache.py` (new) - four tests pinning the cache contract.
