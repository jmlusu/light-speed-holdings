# LIGHTSPEED HOLDINGS — MASTER SPECIFICATION

**Document:** MASTER_SPEC.md
**Status:** Normative implementation specification
**Organization:** LightSpeed Holdings Limited
**Canonical agent count:** 90 AI agents
**Primary objective:** Replace the legacy web experience with a coherent AI-native corporate platform and public-facing company website.

---

# 1. PURPOSE

This document is the single source of truth for the LightSpeed Holdings web experience.

The implementation must represent LightSpeed as an **AI-native company builder and operating company** serving Malawi, SADC, and Africa.

This is an architecture and experience specification, not merely a copywriting brief.

The agent must implement the information architecture, product narrative, interaction model, design language, public/internal boundary, content model, and governance model described here.

If the existing application conflicts with this document, this document takes precedence.

---

# 2. BRAND POSITION

## Company

**LIGHTSPEED HOLDINGS LIMITED**

## Core positioning

LightSpeed is an AI-native company that combines:

- Strategy
- Build
- Govern
- Research & Policy

into an operating model for building, transforming, governing, and scaling AI-enabled organizations.

LightSpeed should be presented as an **AI Company Builder**, not as a generic consulting firm or an AI chatbot company.

## Geographic ambition

**Malawi → SADC → Africa**

The website should communicate African relevance while maintaining international professional standards.

## Brand line

**ASPIRE. ACT. ACHIEVE.**

---

# 3. CORE OPERATING MODEL

LightSpeed operates through four connected capabilities:

## STRATEGY

Turn organizational priorities into executable strategies, operating models, roadmaps, and AI opportunities.

## BUILD

Design and build AI-native workflows, applications, agentic systems, data products, automation, and digital operating capabilities.

## GOVERN

Establish the controls, architecture, policies, standards, risk management, security, data governance, and decision rights required for responsible AI adoption.

## RESEARCH & POLICY

Develop evidence, research, market intelligence, policy analysis, and practical guidance for AI adoption in Malawi, SADC, and Africa.

These capabilities should appear as one connected system rather than four unrelated service categories.

# 6. HUMAN + AI OPERATING MODEL

LightSpeed is not presented as an autonomous company without human accountability.

The operating model is:

**Human leadership + governed AI workforce + systems + data + controls**

Human decision rights remain explicit.

AI agents may research, analyze, draft, automate, monitor, coordinate, and execute authorized workflows.

High-impact decisions require appropriate human oversight.

The website should communicate confidence without implying uncontrolled autonomy.

# 9. PROGRESSIVE DISCLOSURE

The website should not overwhelm visitors with the entire LightSpeed operating model at once.

Use progressive disclosure:

## Layer 1 — Executive

What is LightSpeed?

## Layer 2 — Business

What can LightSpeed do for my organization?

## Layer 3 — Operating model

How does the AI Company Builder work?

## Layer 4 — Architecture

How are agents, data, workflows, and governance connected?

## Layer 5 — Evidence

What has been built, tested, measured, or demonstrated?

## Layer 6 — Technical detail

How does the system work?

The visitor should be able to stop at any layer without being forced through all layers.

# 15. DATA AND CONTENT ARCHITECTURE

The public website should move toward structured, registry-driven content rather than scattering business facts throughout components.

Examples of structured registries:

- services
- solutions
- sectors
- case studies
- insights
- metrics
- capabilities
- agents
- leadership
- FAQs
- CTAs

Business facts should have a clear canonical source.

Avoid hard-coding the same number or claim in multiple unrelated components.

For example, the canonical agent count should be represented once and consumed by relevant views.

---

# 16. DYNAMIC METRICS

Metrics must be treated as governed data.

Examples:

- Agent count
- Projects
- Solutions
- Sectors
- Research outputs
- Active capabilities

Do not duplicate numbers throughout the UI.

If a metric changes, the change should propagate from its canonical data source.

Never use animated counters to make unsupported claims look authoritative.

---

# 17. CONTENT GOVERNANCE

Every significant public claim should have a clear source or owner.

Content states:

- Draft
- Review
- Approved
- Published
- Archived

Avoid publishing unsupported claims.

Claims involving clients, financial performance, partnerships, outcomes, scale, or impact require evidence.

---

# 21. LIGHT AND DARK MODES

Both modes are first-class experiences.

Do not simply invert colors.

Light mode should feel:

- bright
- calm
- spacious
- editorial
- premium

Dark mode should feel:

- deep
- focused
- atmospheric
- technical
- refined

Typography, contrast, surfaces, imagery, shadows, and animation should be tuned independently for each mode.

Respect the user's system preference while providing an explicit theme control where appropriate.

---

# 22. MOTION

Motion should communicate hierarchy and state.

Preferred qualities:

- slow
- fluid
- restrained
- spatial
- intentional

The principle is:

**Slow to the eye. Fast to the mind.**

Use motion for:

- page transitions
- reveal
- navigation
- data visualization
- agent/system relationships
- state changes
- depth

Do not animate every element.

Respect:

`prefers-reduced-motion`

Reduced-motion users must receive a complete experience without decorative animation.

---

# 23. RESPONSIVE DESIGN

Design for:

- desktop
- laptop
- tablet
- mobile

Do not simply shrink the desktop interface.

Reconsider:

- navigation
- information density
- grids
- diagrams
- animations
- typography
- CTA placement
- data visualizations

for smaller screens.

---

# 24. ACCESSIBILITY

Target strong accessibility practices.

Required considerations:

- semantic HTML
- keyboard navigation
- visible focus
- adequate contrast
- descriptive labels
- alt text
- accessible forms
- reduced motion
- readable typography
- logical heading hierarchy
- screen-reader compatibility

Accessibility is part of the product, not a final polish step.

---

# 25. PERFORMANCE

The experience should remain fast despite sophisticated visuals.

Priorities:

1. Content clarity
2. Interaction responsiveness
3. Core Web Vitals
4. Progressive loading
5. Image optimization
6. Lazy loading
7. Animation efficiency
8. Minimal unnecessary JavaScript

Do not add Three.js, GSAP, video, shaders, or other heavy technologies simply because they are available.

Use them only where they materially improve the experience.

---

# 26. TECHNICAL ARCHITECTURE

The implementation should favor:

- modular components
- clear data boundaries
- reusable primitives
- typed interfaces
- centralized design tokens
- structured content
- maintainable state
- predictable routing
- testable logic
- accessible components

Avoid:

- giant page components
- duplicated content
- duplicated constants
- hidden business logic
- unnecessary dependencies
- abandoned experimental code
- legacy compatibility layers that exist only to preserve obsolete UI

The public website is a curated representation of LightSpeed.

- Public
